# Codexterity v0.3.0 — release notes

**Released 2026-09-26.** This release keeps Codexterity working on Codex `26.924`, which stopped
starting at all through Codexterity's previous launch route. Project version `0.3.0`
(`package.json`). Both themes' versions stay `0.1.0`, deliberately: **no colour, font, hero or
token name changed.** The goal was that the themes look exactly as they did on 2026-09-23.

Codexterity is a non-destructive theming layer for OpenAI's Codex Desktop app. It reskins Codex at
runtime and never modifies, patches or re-signs any Codex file. One theme ships: **Captain's Cabin**.

As before, every claim below is either **verified** (something was run and observed) or **built but
unverified** (it exists, and nobody has watched it work).

---

## Why this release exists

Codex `26.924.1866.0` (2026-09-26) requires the process to carry a **Windows package identity**, the
identity a Store app gets only when Windows itself activates it. Codexterity had always started
`ChatGPT.exe` directly as a child process so it could hand the app two environment variables; that
process has no identity, so Codex's own startup failed before any Codexterity code ran, with the
dialog "ChatGPT failed to start. The process has no package identity." **The injector was not the
cause**: plain Codex launched the same way, with no injector attached, failed identically.

## What changed

- **Windows launches Codex with package identity**, through Windows' own
  `Invoke-CommandInDesktopPackage`, so Codex `26.924` starts. This also means the Codexterity
  shortcut can start plain, unthemed Codex again after `cdx restore`.
- **Windows injects the theme over a loopback Chrome DevTools connection.** An identity launch does
  not pass environment variables through, so the old preload route cannot reach Codex; it does pass
  command-line arguments, and Codex honours a debugging-port argument. Codexterity now starts Codex
  with a random, local-only port and a small attacher process applies the stylesheet to every Codex
  page, then exits when Codex does. **This gives up the previous "no debug port ever" guarantee on
  Windows**, knowingly (decision D-0005-1): while a themed Codex runs, any process on the same
  machine that finds the port can control Codex's pages. The port is bound to `127.0.0.1`, is never
  fixed, and is not opened for an unthemed launch (verified: zero listening sockets).
- **The running-instance guard** now uses Windows' process table (`Win32_Process`), because
  `Get-Process` cannot see an identity-launched Codex and the guard would otherwise silently pass.
- **Node.js 22.4 or newer** is now required (the attacher uses Node's built-in WebSocket client).
- **macOS is unchanged** and still uses the preload route; it remains built but unverified.

## Verified (Windows, this machine, Codex `26.924.1866.0`)

- Installed from the built package, then launched through the **real Start-menu shortcut**: both
  **Captain's Cabin** and **Deep Navy Portrait** painted. The injector log for each shows the theme
  loaded, all three Codex pages themed, the home hero painting, the brass active-row mark at 2×16 px,
  Literata / Fraunces / Monaspace Neon loadable, and `sidebar-panel`, `sidebar-active-row`,
  `heading-display` and `home-hero` PRESENT.
- The themed launcher exits cleanly when Codex closes; with Codex already open it refuses and
  names the PID.
- An unthemed launch through the same route starts stock Codex with no port open.
- `npm test`: **408/408**.

## Known gaps

- The very first window may show stock Codex for a fraction of a second before the theme lands,
  because the theme is now applied after the page exists rather than before it paints. Later
  navigations are themed before first paint.
- macOS: unverified, as in every release.
